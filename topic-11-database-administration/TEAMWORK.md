## Контекст теми
За створення базової структури ролей, користувачів і грантів з дотриманням least privilege відповідав Oleksandr Chura, на цю структуру опиралися у роботі над своїми ролями і користувачами решта команди. Oleh Svyrydenko провів security review та додав гранулярні обмеження — `REVOKE DELETE` на таблиці `memberships` для захисту аудит-історії цін, `REVOKE TRUNCATE` для всіх неадмінських ролей, а також гранти на sequences та ENUM-типи для коректної роботи в Supabase.

## Коротке обґрунтування командного підходу
1. Чому обрали саме такі ролі та рівні доступу: ролі відповідають реальним учасникам життєвого циклу застосунку — адміністратор (`gym_admin`), бекенд-сервіс (`gym_app`), розробник (`gym_developer`), міграційний процес (`gym_migration`) та QA-тестувальник (`gym_tester`). Кожна роль отримує лише ті права, які потрібні для її функції (принцип least privilege): тестувальник — тільки `SELECT`, застосунок і розробник — повний DML без DDL, міграція — DML + DDL для еволюції схеми, адмін — повний контроль включно з `CREATEROLE`.
2. Як розподілили відповідальність за безпекову модель: Oleksandr Chura створив базову структуру ролей, користувачів і грантів з дотриманням least privilege, яку наслідували у роботі над своїми ролями і користувачами решта команди. Oleh Svyrydenko провів security review та додав гранулярні обмеження — `REVOKE DELETE` на таблиці `memberships` для захисту аудит-історії цін, `REVOKE TRUNCATE` для всіх неадмінських ролей, а також гранти на sequences та ENUM-типи для коректної роботи в Supabase.
3. Як перевірили, що ролі реально відрізняються правами: у скрипті є секція Manual Test Queries (розділ 8), яка описує конкретні команди для перевірки під кожним користувачем — наприклад, `tester_user` може виконати `SELECT`, але не `INSERT`; `app_user` може вставляти дані, але не може `DELETE FROM gym.memberships`; `migration_user` може створювати нові таблиці (`CREATE TABLE`). Ці тести запускалися вручну з'єднання під відповідними користувачами в Supabase.
